# windows_toast.rs

Windows toast notification backend for the OpenFrame app. Builds and posts native Windows toast XML, handling two separate activation paths: a hand-built `openframe-console://notify` URI for body/"Open" clicks (reaching a running or cold-started instance via argv), and a COM background activator (`windows_activator`) for Approve/Reject buttons and inline Reply, since protocol activation cannot carry text input or run against an already-live process.

## Key Components

- **`post`** — Entry point for posting a notification. Builds the toast XML, computes an optional replacement tag (only for approval requests), and dispatches `show` on a background thread so a WinRT failure never blocks the caller.
- **`show`** — Loads the XML into a `XmlDocument`, creates a `ToastNotification`, best-effort tags/groups it for replacement semantics, optionally suppresses the popup for `Delivery::Update`, and displays it via `ToastNotificationManager`.
- **`ensure_logo`** — Lazily writes the embedded app icon to the app-config directory (resolved once per process via `OnceLock`), since the notification platform resolves the icon out-of-process and must find it on disk even after the app exits.
- **`write_logo`** — Writes the logo atomically through a PID-suffixed temp file plus rename, avoiding torn reads that Windows would otherwise cache until the notification service restarts.
- **`toast_tag`** — Folds an arbitrary id down to Windows' 64-character tag limit, keeping only ASCII alphanumerics, `-`, and `_`.
- **Constants** — `TITLE_LIMIT`, `BODY_LIMIT`, `TOAST_XML_BUDGET` (payload size guard against the platform's ~5 KB silent-drop cap), `TAG_LIMIT`, `TOAST_GROUP`, `REPLY_INPUT_ID`, and action name constants (`APPROVE_ACTION`, `REJECT_ACTION`, `REPLY_ACTION`).

The XML-building and argument-encoding logic is compiled on non-Windows targets too (e.g. macOS CI), since those are the parts most likely to fail silently inside the notification platform rather than via a stack trace.

## Usage Example

```rust
#[cfg(target_os = "windows")]
fn notify_approval(app: &tauri::AppHandle, request_id: String, user_id: String) {
    windows_toast::post(
        app,
        "Approval needed".to_string(),
        "A device requires sign-off".to_string(),
        Some(serde_json::json!({ "requestId": request_id })),
        Some(user_id),
        ActionKind::Approval,
        Delivery::New,
    );
}
```

Replacement/update behavior relies on tagging: posting again with the same `requestId` in `click` reuses the same toast tag, so a later `Delivery::Update` silently replaces the original banner instead of stacking a new one.
