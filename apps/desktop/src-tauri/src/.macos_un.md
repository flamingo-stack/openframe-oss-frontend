## macos_un.rs

Implements the macOS `UNUserNotificationCenter` backend for OpenFrame's desktop notification system in production (bundled) builds. This is the macOS counterpart to the shared `notification_actions` module, providing OS-level notification delivery, actionable buttons (Approve/Reject, inline Reply), and click routing that survives process restarts.

It replaces the deprecated `NSUserNotificationCenter` path because UN reports clicks consistently across all delivery contexts (live banner, Notification Center, or cold app launch), whereas the legacy API only caught live-banner clicks.

## Key Components

- **`init(app: &AppHandle)`** — Installs the notification delegate and registers action categories. No-ops for dev builds or apps without a bundle identifier (UN APIs require one). Must be called early during Tauri setup to catch cold-start click responses.
- **`ensure_authorized()`** — Requests notification permission from macOS exactly once; denial is handled gracefully (user-controlled via System Settings).
- **`post(title, body, click, user_id, kind)`** — Fires an OS notification off the main thread. Embeds the click payload and delivering user ID into the notification's `userInfo` so actions can be validated against the live session later, even after a restart.
- **`category_for(kind: ActionKind)`** — Maps an `ActionKind` (`Default`, `Approval`, `Message`) to its registered category identifier.
- **`register_categories(center)`** — Defines the three notification categories and their buttons: plain "Open", "Approve"/"Reject" (destructive) for AI tool approvals, and "Reply" (text input) + "Open" for Mingo messages.
- **Constants** — Category IDs (`CATEGORY_DEFAULT`, `CATEGORY_APPROVAL`, `CATEGORY_MESSAGE`), action IDs (`OPEN_ACTION_ID`, `APPROVE_ACTION_ID`, `REJECT_ACTION_ID`, `REPLY_ACTION_ID`), and `userInfo` keys (`PAYLOAD_KEY`, `USER_KEY`).
- **`ROUTER` / `ACTIVE`** — Process-wide statics: `ROUTER` holds the `AppHandle` used to route delegate callbacks back into the app shell; `ACTIVE` gates whether the backend is usable (false in dev or unbundled builds).

The `NotificationDelegate` (defined via `define_class!` elsewhere in this module) implements `UNUserNotificationCenterDelegate`, decoding `UNNotificationResponse`/`UNTextInputNotificationResponse` into an `Action`/`ActionContext` and dispatching through `deliver_click` and `notification_actions::run_action`.

## Usage Example

```rust
// During Tauri app setup:
notifications::macos_un::init(&app_handle);
notifications::macos_un::ensure_authorized();

// Later, when an event requires user attention:
notifications::macos_un::post(
    "Tool Approval Required".to_string(),
    "Mingo wants to run `delete_file`".to_string(),
    Some(serde_json::json!({ "action": "approve", "request_id": "abc123" })),
    Some("user-42".to_string()),
    ActionKind::Approval,
);
```

**Note:** This backend is inert in `tauri dev` builds and in any process lacking a macOS bundle identifier — `post` silently drops notifications in those cases, logging at debug level.
