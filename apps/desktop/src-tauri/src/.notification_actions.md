# notification_actions.rs

## Overview

Platform-agnostic core of the notification action-button system for the Tauri desktop shell. It decides which action buttons a notification earns (`ActionKind`), executes pressed buttons against the chat gateway, tracks which approval requests have already been settled, and notifies any open window when a background action changes a conversation. Platform-specific code (macOS's `macos_un`, Windows's `windows_toast`/`windows_activator`) handles OS plumbing and defers to this module for the actual decision logic.

## Key Components

- **`ActionKind`** — Enum (`Default`, `Approval`, `Message`) describing which buttons a notification should display, derived from the click payload.
- **`kind_for` / `live_kind_for`** — Compute the button set for a payload; `live_kind_for` additionally suppresses buttons for approvals already known to be resolved.
- **`approval_request_id` / `dialog_id`** — Extract the approval request id or conversation id from a click payload, gated by notification type (`TICKET_APPROVAL_REQUEST`, `MINGO_APPROVAL_REQUEST`, `ADMIN_AI_MESSAGE`).
- **`note_resolution`** — Records settled approval verdicts (`APPROVED`, `REJECTED`, `CANCELLED`) from republished envelopes, keeping local state in sync with the gateway.
- **`RESOLVED` / `remember_resolved` / `is_resolved` / `forget_resolved`** — A bounded, in-memory ring buffer (`RESOLVED_MEMORY = 64`) of settled approval request ids, cleared on sign-out.
- **`Action`** — Enum (`Approve`, `Reject`, `Reply(String)`) representing a pressed button, with `done()`, `verb()`, and `failed()` helpers for user-facing banner text.
- **`ActionContext`** — Snapshot of data needed to process a button press (title, payload, user id), lifted out of the OS callback before async work begins.
- **`spawn`** — Entry point called by platform backends to run an action asynchronously and report the outcome via a new notification.
- **`run_action`** — Session-gated executor: verifies an authenticated session matches the notification's intended user before performing the write against the gateway.
- **`DIALOG_CHANGED_EVENT`** — Tauri event (`chat:dialog-changed`) emitted to the main window so open UI can refresh after a background action.

## Usage Example

```rust
// Called from a platform-specific notification click handler
use crate::notifications::notification_actions::{ActionContext, Action, spawn, live_kind_for};

// Decide which buttons to show when building the notification
let kind = live_kind_for(click_payload.as_ref());

// When the user presses "Approve" on a delivered notification:
let context = ActionContext {
    title: original_title,
    payload: click_payload,
    user_id: notification_user_id,
};
spawn(&app_handle, context, Action::Approve);
```

Platform backends construct an `ActionContext` from decoded OS callback data and hand it off to `spawn`, which runs the session-gated write asynchronously, emits `chat:dialog-changed` on success, and posts a follow-up notification reporting success or failure.
