## notification_actions.rs

This module implements the platform-independent decision logic for notification action buttons: which buttons a notification earns, what pressing one does, and how the outcome is reported back. Platform-specific backends (macOS `UNNotification` categories, Windows toast XML/COM activator) handle their own plumbing and delegate to this shared logic.

## Key Components

- **`ActionKind`** — Enum (`Default`, `Approval`, `Message`) determining which button set a notification gets, derived from its click payload.
- **`kind_for` / `live_kind_for`** — Compute the button set for a payload; `live_kind_for` additionally suppresses buttons for approvals already resolved.
- **`approval_request_id` / `dialog_id`** — Extract the approval or conversation identifier a payload refers to, gating button offers on whether the id actually survived payload projection.
- **`note_resolution`** — Records a settled approval verdict (`APPROVED`, `REJECTED`, `CANCELLED`) from a republished envelope, keeping local state in sync with the gateway.
- **`RESOLVED`** — Bounded in-memory ring buffer (`VecDeque`, capacity `RESOLVED_MEMORY`) tracking recently settled approval request ids.
- **`forget_resolved`** — Clears resolved-request memory on sign-out.
- **`Action`** — Enum (`Approve`, `Reject`, `Reply(String)`) representing a pressed button, with helpers for success/failure banner text.
- **`ActionContext`** — Struct carrying everything (`title`, `payload`, `user_id`) a background action needs, decoupled from OS-specific response objects.
- **`spawn`** — Entry point called by platform backends after decoding a button press; runs the action asynchronously and reports the outcome.
- **`run_action`** — Core session-gated execution: verifies an active, matching signed-in session before performing approve/reject/reply writes against the gateway.
- **`announce_dialog_change`** — Emits a `chat:dialog-changed` event to the main window so open UI can refetch after a background write.
- **`Outcome`** — Internal enum (`Done`, `AlreadyResolved`) distinguishing a successful write from a no-op on an already-settled request.

## Usage Example

```rust
// Called from a platform backend after decoding a notification button press
use crate::notifications::notification_actions::{spawn, Action, ActionContext};

let context = ActionContext {
    title: "Approval needed".to_string(),
    payload: Some(click_payload),
    user_id: Some("user-123".to_string()),
};

spawn(&app_handle, context, Action::Approve);
```

```rust
// Determining button set before building a platform notification
use crate::notifications::notification_actions::live_kind_for;

let kind = live_kind_for(click_payload.as_ref());
```
