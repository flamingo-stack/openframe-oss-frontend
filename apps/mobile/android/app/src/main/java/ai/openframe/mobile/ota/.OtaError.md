Custom exception type representing OTA (over-the-air) update failures, used by the mobile OTA update pipeline to classify and signal errors during bundle verification and extraction.

## Key Components

- **`OtaError`** - Checked exception extending `Exception`, carrying a structured error `code` alongside a human-readable message.
- **`Code` (enum)** - Enumerates all possible failure categories: `ENVELOPE`, `UNKNOWN_KEY`, `SIGNATURE`, `PAYLOAD`, `SIZE`, `SHA256`, `XZ`, `TAR`, `ENTRY_TYPE`, `ENTRY_NAME`, `DUPLICATE`, `NO_INDEX`, `NO_ENV`, `HAS_ENV`, `NO_HEAD`. These codes correspond to the shared OTA test cases defined in the mobile OTA fixtures.
- **`code` (field)** - Public, final field exposing the error's `Code` for programmatic handling by callers.
- **`isContentRefusal()`** - Determines whether the failure stems from the bundle's *content* (e.g., malformed archive, duplicate entries, missing index/head) as opposed to a *transport* issue (e.g., size or SHA-256 mismatch). Content refusals indicate the bundle's version should be permanently marked bad, since it would fail verification on every retry. Transport-related errors instead suggest the download should simply be retried.

## Usage Example

```java
try {
    verifyAndExtractOtaBundle(bundlePath);
} catch (OtaError e) {
    if (e.isContentRefusal()) {
        // Permanently mark this OTA version as bad; retrying won't help
        otaVersionStore.markBad(bundleVersion, e.code);
    } else {
        // Likely a transient download issue (size/SHA256 mismatch); retry
        otaDownloader.retry(bundleVersion);
    }
    log.error("OTA update failed: code=" + e.code, e);
}
```

This exception is typically thrown by the OTA verification/extraction logic and caught by the update manager to decide whether to retry the download or blacklist the problematic version.
