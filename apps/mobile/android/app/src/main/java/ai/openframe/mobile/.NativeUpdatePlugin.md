## NativeUpdatePlugin.java

Capacitor plugin that exposes the Android native-update bridge to the web frontend under the JS name `"NativeUpdate"`. It is the Android counterpart to `ios/App/App/NativeUpdatePlugin.swift`, exposing identical methods so the shared frontend code in `native-shell.ts` can drive updates uniformly across platforms. By design, none of its methods accept a path, URL, or version from the page — the native shell alone decides which bundle is active and where updates come from.

## Key Components

- **`NativeUpdatePlugin`** — `@CapacitorPlugin(name = "NativeUpdate")` class exposing update lifecycle methods to JavaScript.
- **`update()`** — Private helper returning the singleton `NativeUpdate` instance for the current context.
- **`notifyReady(PluginCall)`** — Signals that the current bundle has loaded successfully; resolves with an empty object.
- **`getState(PluginCall)`** — Resolves with the current update state as a `JSObject`.
- **`check(PluginCall)`** — Triggers an update check; never rejects, since a check finding nothing simply leaves state unchanged.
- **`applyPending(PluginCall)`** — Applies a pending downloaded bundle by switching the bridge's server base path; rejects with `NO_PENDING` if no bundle is staged.

## Usage Example

This plugin is invoked from the frontend via Capacitor's JS bridge, not directly from Java:

```java
// Registered automatically via @CapacitorPlugin during Capacitor bridge init.
// Typical native-side flow:
NativeUpdatePlugin plugin = new NativeUpdatePlugin();

// On app resume/start, check for a new bundle
plugin.check(call); // resolves with current state regardless of outcome

// After a successful download/verify, apply it
plugin.applyPending(call); // switches bridge.setServerBasePath on the main thread
```

From the frontend (TypeScript), these methods are called through `native-shell.ts`, e.g. `NativeUpdate.check()`, `NativeUpdate.getState()`, and `NativeUpdate.applyPending()`, keeping update logic entirely on the native side.
