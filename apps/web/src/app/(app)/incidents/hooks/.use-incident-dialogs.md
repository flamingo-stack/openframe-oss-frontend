# use-incident-dialogs.ts

React Query hooks that resolve the most recent active Mingo chat dialog associated with an incident, used to drive "Fix with Mingo" / reopen-chat buttons in incident UI without blocking rendering on chat-service failures.

## Key Components

- **`latestIncidentDialogQuery(insightId)`** — Builds a `queryOptions` config keyed on `['mingo-dialogs', 'insight', insightId]`. Posts a GraphQL query to `/chat/graphql` filtering active ADMIN dialogs by `insightId`, returning the first matching `DialogNode` or `null`. Any transport error or GraphQL error envelope resolves to `null` (no throw, no toast) so callers can safely fall back to "start a new chat."
- **`useLatestIncidentDialog(insightId)`** — Suspense-based hook for the incident detail header. Returns `DialogNode | null`. Suspends until resolved so the header renders once with the correct button state.
- **`IncidentDialogLookup`** — Type alias for a readonly record mapping incident id → `DialogNode | null | undefined` (undefined while pending).
- **`useLatestIncidentDialogs(insightIds)`** — Non-suspending hook for table/list views. Fans out one `fetchQuery` per incident id under a single query keyed by the sorted id set, populating the same per-id cache entries used by `useLatestIncidentDialog`. Uses `keepPreviousData` to avoid blanking already-resolved rows while new ids load.

## Usage Example

```typescript
import { useLatestIncidentDialog, useLatestIncidentDialogs } from './use-incident-dialogs';

// Incident detail header (suspends)
function IncidentHeader({ insightId }: { insightId: string }) {
  const dialog = useLatestIncidentDialog(insightId);
  return dialog ? <ReopenChatButton dialogId={dialog.id} /> : <StartChatButton />;
}

// Incident table column (non-blocking)
function IncidentsTable({ insightIds }: { insightIds: string[] }) {
  const dialogsById = useLatestIncidentDialogs(insightIds);
  return (
    <>
      {insightIds.map(id => (
        <MingoCell key={id} dialog={dialogsById[id]} />
      ))}
    </>
  );
}
```

Both hooks share the same cache entries (keyed per `insightId`), so a dialog resolved via the table lookup is immediately available when the detail header mounts for that incident.
