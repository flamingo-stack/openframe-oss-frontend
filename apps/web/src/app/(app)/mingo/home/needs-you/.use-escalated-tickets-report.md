## use-escalated-tickets-report.ts

A React hook that powers the "Needs you" dashboard widget by fetching Tech Required tickets that end users have escalated, surfacing them even if buried deep in a support lane.

It composes two queries — ticket statuses (to resolve the Tech Required status IDs) and the escalated tickets themselves — then normalizes both into a single `SourceReport` result with loading, error, and ready states.

## Key Components

- **`useEscalatedTicketsReport(gate: FeatureFlagGate): SourceReport`** — Main hook export. Returns one of three report shapes (`loading`, `error`, or `ready`) based on the combined state of the status and ticket queries.
- **`ESCALATED_CANDIDATES`** — Constant (5) controlling how many candidate tickets are fetched, allowing for dedupe against other "Needs you" sources.
- **`NO_IDS`** — Empty fallback array used when status data isn't yet available, preventing an unnecessary fetch.
- Query key: `[...dialogsQueryKeys.all, 'needsYouEscalated', statusIds]` — scoped under the shared `dialogs` key so any ticket mutation invalidates it, but distinct from the board's own infinite-query cache.

## Usage Example

```typescript
import { useEscalatedTicketsReport } from './use-escalated-tickets-report';

function NeedsYouEscalatedCard({ gate }: { gate: FeatureFlagGate }) {
  const report = useEscalatedTicketsReport(gate);

  if (report.status === 'loading') return <Skeleton />;
  if (report.status === 'error') {
    return (
      <ErrorState offline={report.isOffline} onRetry={report.retry} />
    );
  }

  return (
    <ul>
      {report.rows.map(row => (
        <TicketRow key={row.id} row={row} />
      ))}
    </ul>
  );
}
```

**Notes:**
- Pass `gate='off'` to disable fetching entirely (e.g., behind a feature flag) — the hook reports `closed` state internally and short-circuits queries.
- The hook always refetches on mount (`refetchOnMount: 'always'`) to ensure fresh data each time the dashboard is viewed, while relying on `staleTime` to avoid redundant background refetches.
- Errors are prioritized from the statuses query first, then the tickets query, with a unified `retry()` callback that refetches whichever failed.
