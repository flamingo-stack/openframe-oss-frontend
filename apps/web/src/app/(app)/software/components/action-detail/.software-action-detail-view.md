# software-action-detail-view.tsx

Renders the Software Update/Install Details page: a single software action run showing its header, summary, and per-device execution logs. Rather than using a shared `PageLayout` that would block the whole page on one query, this component splits the page into three independent "islands" (header, summary, logs), each fetching the same `softwareAction` query but rendering/loading its own fallback state independently.

## Key Components

- **`SoftwareActionDetailView`** — Top-level component; accepts `actionId` and an optional `loading` flag (used while the feature flag module hasn't resolved yet), and composes the header, summary, and logs islands alongside an `ExecutionsTabShell` for search.
- **`softwareActionDetailViewQuery`** — GraphQL query fetching a `softwareAction` by `id`, spreading fragments for the header, summary, and logs components.
- **`ActionHeaderIsland` / `ActionHeaderReader`** — Loads and renders `ActionDetailHeader` in its own `LoadingSuspense` boundary.
- **`ActionSummaryIsland` / `ActionSummaryReader`** — Loads and renders `ActionDetailSummary` independently.
- **`ActionLogsIsland` / `ActionLogsReader`** — Loads and renders `ActionDetailLogs`, using `fetchPolicy="store-or-network"` to reuse cached data from the other islands' requests.

## Usage Example

```typescript
import { SoftwareActionDetailView } from './software-action-detail-view';

export default function SoftwareActionPage({ params }: { params: { actionId: string } }) {
  return <SoftwareActionDetailView actionId={params.actionId} />;
}
```

Each island checks `useLoadingScope()` to render a data-less fallback (e.g., `<ActionDetailHeader action={null} />`) while in a loading/preview scope, avoiding an actual network read until the real `actionId` is available. This pattern ensures the logs' search toolbar (inside `ExecutionsTabShell`) is interactive from the first frame, independent of query completion for the header or summary.
