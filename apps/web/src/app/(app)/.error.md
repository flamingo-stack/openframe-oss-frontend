## error.tsx

Next.js error boundary component scoped to the signed-in `(app)` route segment, rendered *inside* `AppLayout` so that unrecovered errors no longer blow away the app's chrome (header, nav, safe-area).

This boundary exists because `useLazyLoadQuery` (Relay) throws on failed requests rather than returning an error state, and the shared environment only retries transient failures for a bounded budget. A sustained outage therefore surfaces as a thrown error. Previously, the root `app/error.tsx` — positioned *above* `(app)/layout.tsx` — was the only boundary catching these, which meant any data failure replaced the entire app shell instead of just the affected content. Most pages now handle their own data failures inline via `ContentErrorBoundary`; reaching this boundary means an error escaped that inline handling and bubbled up from outside a page's data region.

## Key Components

- **`AppError`** — Default export; a Next.js `error.tsx` boundary component for the `(app)` segment. Accepts the standard Next.js error boundary props (`error`, `reset`) and delegates rendering to `RouteError` with a distinguishing `label` for debugging/telemetry purposes.

## Usage Example

This file is a Next.js convention file and is not imported manually — placing it at `app/(app)/error.tsx` automatically wires it up as the error boundary for that route segment.

```typescript
// app/(app)/error.tsx
'use client';

import { RouteError } from '../components/route-error';

export default function AppError({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return <RouteError error={error} reset={reset} label="App Error Boundary" />;
}
```

When a data-fetching call (e.g., a Relay `useLazyLoadQuery`) throws an unhandled error within the `(app)` segment and no closer `ContentErrorBoundary` intercepts it, Next.js renders this component instead of unmounting the entire `AppLayout` shell, preserving navigation and chrome while showing an error state with a `reset` option to retry.
