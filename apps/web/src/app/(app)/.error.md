This file defines the error boundary for the signed-in `(app)` route segment in Next.js, ensuring thrown errors are caught without destroying the surrounding `AppLayout` shell (header, nav, safe-area chrome).

## Key Components

- **`AppError`** — Default export; a Next.js `error.tsx` boundary component scoped to the `(app)` segment, rendered *inside* `(app)/layout.tsx` rather than above it.
- **`RouteError`** — Shared presentational component (imported from `../components/route-error`) used to render the actual error UI, labeled `"App Error Boundary"` for this boundary.

## Usage Example

This file is a Next.js framework convention file and is not imported manually — Next.js automatically mounts it when a component inside the `(app)` segment throws:

```typescript
// app/(app)/error.tsx
'use client';

import { RouteError } from '../components/route-error';

export default function AppError({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return <RouteError error={error} reset={reset} label="App Error Boundary" />;
}
```

**Why placement matters:** Next.js resolves `error.tsx` boundaries by directory nesting. Placing it under `(app)` (rather than at `app/error.tsx`, above `(app)/layout.tsx`) means only the page content is replaced on error — the `AppLayout` chrome remains mounted. This specifically matters for Relay-powered routes (Scripts, Knowledge Base, Logs, Notifications, Worktime) where `useLazyLoadQuery` throws on sustained failures after `lib/relay/environment.ts`'s retry budget is exhausted. Most in-page data errors are now caught earlier by `ContentErrorBoundary`; reaching this boundary indicates an error originating outside a page's data region.
