# use-reopen-ticket.ts

A React Query mutation hook that implements the admin "reopen ticket" workflow, transitioning a ticket out of a terminal status and optionally reassigning it.

## Key Components

- **`ReopenTicketInput`** — Interface describing the mutation payload: `ticketId`, `toStatusId`, `toStatusKind` (unused placeholder), `assigneeId`, `currentAssigneeId`, and `reason` (currently not wired to any backend field).
- **`reopenTicketApi(input)`** — Internal async function that:
  1. Calls `ticketService.transitionTicket` to move the ticket out of its terminal status (this is what triggers the backend's admin-reopen behavior, including chat card and notification events).
  2. If `assigneeId` differs from `currentAssigneeId`, issues an `ASSIGN_TICKET_MUTATION` or `UNASSIGN_TICKET_MUTATION` GraphQL call via `apiClient`, throwing on any `userErrors`.
- **`useReopenTicket()`** — Exported hook wrapping `reopenTicketApi` in `useMutation`. On success, invalidates the ticket detail query, all dialog queries, and shows a success toast. On error, shows a destructive toast with the error message.

## Usage Example

```typescript
import { useReopenTicket } from './use-reopen-ticket';

function ReopenTicketModal({ ticket }: { ticket: Ticket }) {
  const reopenTicket = useReopenTicket();

  const handleReopen = (toStatusId: string, assigneeId: string | null) => {
    reopenTicket.mutate({
      ticketId: ticket.id,
      toStatusId,
      assigneeId,
      currentAssigneeId: ticket.assigneeId,
      reason: null,
    });
  };

  return (
    <button onClick={() => handleReopen('status-open', ticket.assigneeId)} disabled={reopenTicket.isPending}>
      Reopen Ticket
    </button>
  );
}
```

**Notes:**
- Deliberately avoids calling the client-facing "request reopen" chat verb; admins must use `transitionTicket` directly, since the backend rejects admin-initiated chat reopen requests.
- The `reason` field is collected by the UI but has no backend wire yet—passed through for future use once an admin-facing field exists.
- Assignment changes are only sent when they differ from the ticket's prior assignee, preserving the default "restore previous assignee" behavior.
