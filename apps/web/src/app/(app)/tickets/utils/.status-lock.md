Utility module for determining whether a ticket's status field should be locked in the UI due to a pending tool-approval request, mirroring server-side transition policy validation.

## Key Components

- **`STATUS_LOCKED_BY_APPROVAL_REASON`** — Constant string explaining why status editing is disabled; intended for display in tooltips or disabled-state messages.
- **`isStatusLockedByPendingApproval(ticket)`** — Predicate function that returns `true` when a ticket is in `TECH_REQUIRED` status kind **and** has a pending approval request. Safely handles `null`/`undefined` input.

## Usage Example

```typescript
import { isStatusLockedByPendingApproval, STATUS_LOCKED_BY_APPROVAL_REASON } from './status-lock';

const ticket = {
  statusKind: 'TECH_REQUIRED',
  pendingApproval: { id: 'req-123', toolName: 'reset-password' },
};

if (isStatusLockedByPendingApproval(ticket)) {
  console.log(STATUS_LOCKED_BY_APPROVAL_REASON);
  // Disable the status dropdown in the UI
}
```

```vue
<script setup lang="ts">
import { computed } from 'vue';
import { isStatusLockedByPendingApproval, STATUS_LOCKED_BY_APPROVAL_REASON } from './status-lock';

const props = defineProps<{ ticket: { statusKind?: string; pendingApproval?: unknown } }>();

const statusLocked = computed(() => isStatusLockedByPendingApproval(props.ticket));
</script>

<template>
  <select :disabled="statusLocked" :title="statusLocked ? STATUS_LOCKED_BY_APPROVAL_REASON : undefined">
    <!-- status options -->
  </select>
</template>
```

**Note:** This logic must stay in sync with the server-side `TicketTransitionPolicyValidator` rule, since `pendingApproval` already excludes escalate-to-human offers on the backend.
