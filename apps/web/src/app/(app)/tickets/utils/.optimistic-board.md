# optimistic-board.ts

Implements optimistic cache updates for drag-and-drop ticket moves on a Kanban-style board, using TanStack Query's cache to instantly reflect moves between status columns before server confirmation, with rollback support on failure.

## Key Components

- **`OptimisticMoveInput`** — Describes a ticket move: ticket ID, source/target status columns, and sibling tickets (`afterTicketId`/`beforeTicketId`) for positioning.
- **`OptimisticMoveSnapshot`** — Captures prior cache state (board column entries + ticket detail) for rollback.
- **`invalidateBoardColumns(queryClient, statusIds)`** — Invalidates all filter variants of board column queries matching the given status IDs, using a predicate match rather than exact key match.
- **`applyOptimisticMove(queryClient, input)`** — Applies the move immediately to the cache: removes the ticket from its source column, inserts it into the target column (or repositions within the same column), updates the ticket detail cache, and returns a snapshot for potential rollback.
- **`rollbackOptimisticMove(queryClient, snapshot)`** — Restores the cache entries captured in the snapshot, reverting an optimistic move if the mutation fails.

Internal helpers (`isBoardQueryKey`, `findDialogInCache`, `removeFromColumn`, `insertIntoColumn`) handle query key matching, locating a ticket across paginated cache entries, and immutable page updates.

## Usage Example

```typescript
import { applyOptimisticMove, rollbackOptimisticMove, invalidateBoardColumns } from './optimistic-board';

async function moveTicket(queryClient: QueryClient, input: OptimisticMoveInput) {
  const snapshot = applyOptimisticMove(queryClient, input);

  try {
    await ticketService.moveTicket(input);
    invalidateBoardColumns(queryClient, [input.sourceStatusId, input.targetStatusId]);
  } catch (error) {
    rollbackOptimisticMove(queryClient, snapshot);
    throw error;
  }
}
```

This pattern is typically used in a drag-and-drop handler: apply the move optimistically for instant UI feedback, then either confirm with a background refetch/invalidation or roll back if the server call fails.
