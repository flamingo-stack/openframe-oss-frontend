# Queries

Client component rendering the "Queries" monitoring page — a searchable, paginated list of fleet-wide queries with add/delete actions, empty-state onboarding, and error/offline handling.

## Key Components

- **`Queries`** — Default page component that composes:
  - `useApiParams` + `useSearchParam` for URL-synced, debounced search input
  - `useQueries` hook for fetching queries, loading/offline/error state, and `deleteQuery` mutation
  - Client-side pagination via `visibleCount` (increments of `PAGE_SIZE = 20`) and infinite scroll
  - `useStickyToolbar` for a sticky search bar above the table
  - Row-to-`QueryTableRow` mapping with per-row actions (view details, delete)
  - `EmptyState` (via `canClaimEmpty` guard) shown only when data has loaded successfully and the list is truly empty
  - `SectionLoadError` strip shown on error/offline, paired with a matching empty-state message in the table to avoid duplicate/misleading "no data" messaging
  - `ConfirmDeleteMonitoringModal` for delete confirmation

## Usage Example

This component is intended to be rendered directly as a route page (e.g., `app/monitoring/queries/page.tsx`):

```typescript
import { Queries } from '@/app/monitoring/queries/queries';

export default function QueriesPage() {
  return <Queries />;
}
```

Key behavioral notes:
- Search typing updates local state immediately for responsiveness; the URL param (`search`) and filtering only update after a 300ms debounce, avoiding excessive re-renders/navigation.
- `canClaimEmpty` (from `lib/query-state.ts`) is the single source of truth for whether a zero-length list means "genuinely empty" versus "failed or offline load" — both the page-level `EmptyState` and the table's inline empty message respect this flag so they never contradict the error strip above them.
- `LOAD_ERROR_MESSAGE` is defined once and reused in both the error strip and the table's fallback message to keep wording consistent.
