The first step of cancelling a subscription: what it costs (the date it runs to, what the workspace loses) and why
(a cancellation reason, with a comment for "Other").

## Key Components

| Export / Component | Description |
|---|---|
| `CancelSubscriptionModal` | Renders nothing while closed (so every opening starts from an empty form), else `CancelSubscriptionForm` |
| `CancelReason` | Union of the reasons: `TOO_EXPENSIVE`, `NOT_USING_ENOUGH`, `MISSING_FEATURE`, `TECHNICAL_ISSUES`, `OTHER` |
| `CancelSubscriptionForm` | Internal. The dialog: the end date, a fixed sentence, the data-loss box, the reason select and the comment |
| `cancelSubscriptionModalQuery` | Relay query spreading `cancellationEffectiveDate_query` and `dataLossCoreRows_query` |

## Usage Example

```typescript
import { CancelSubscriptionModal, type CancelReason } from './cancel-subscription-modal';

<CancelSubscriptionModal
  isOpen={isModalOpen}
  isPending={isCancelling}
  onClose={() => setModalOpen(false)}
  onConfirm={(reason: CancelReason, comment: string) => handleCancelSubscription(reason, comment)}
/>
```

## Behavior Notes

- The two read parts are islands over one query (`store-or-network`, one fetch): each paints as it resolves.
- While a part loads, its `LoadingSuspense` fallback is the same component with no data (`query={null}`), which draws
  its own loading form: the date a bar of its line, the data-loss rows their bars. No separate skeleton.
- The facts are context, not a gate: a failed read drops that part and the cancellation can still be confirmed.
- Flagged modules count on their own queries (`DataLossModuleRows`).
- Continue is disabled until a reason is chosen; the comment box appears only for `OTHER`.
