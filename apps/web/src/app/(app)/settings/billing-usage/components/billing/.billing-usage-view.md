# billing-usage-view.tsx

Entry point component for the `/settings/billing-usage` route that conditionally renders either a usage-only view or a full billing view, based on build-time visibility flags. It also lazy-loads the billing content so mobile builds (where payments are hidden) never download billing-related code.

## Key Components

- **`BillingUsageContent`** — Dynamically imported (`next/dynamic`, `ssr: false`) wrapper around the actual billing content module. Keeping this lazy ensures builds that hide billing (e.g., mobile) never bundle the payment/cancel/resume/checkout logic.
- **`BillingUsageCodePending()`** — Loading placeholder rendered while `BillingUsageContent`'s code is downloading. Reconstructs the page shell (`BillingPageFrame` + `BillingSections`) using only static modules, passing `null` data and letting each section render its own loading state.
- **`BillingUsageView({ loading })`** — Exported entry component. Uses `isBillingHidden()` to decide, before any component mounts, whether to render `UsageView` (consumption-only, no pricing query) or `BillingUsageContent` (full billing page, self-renders read-only via `isBillingReadOnly()` on desktop builds where applicable).

## Usage Example

```typescript
import { BillingUsageView } from './billing-usage-view';

// In a settings route/page component
export default function SettingsBillingUsagePage() {
  return <BillingUsageView />;
}

// While upstream data/gates are resolving
export function SettingsBillingUsagePageLoading() {
  return <BillingUsageView loading />;
}
```

The component requires no props beyond the optional `loading` flag. Visibility behavior (mobile vs. desktop, read-only vs. interactive) is controlled entirely by `lib/billing-visibility.ts`, so callers don't need to branch on build type themselves.
