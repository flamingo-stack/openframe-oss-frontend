# billing-sections.tsx

Composes the main body of the billing page, assembling usage counters, notices, plan details, and invoice history into a single consistent layout. It uses Relay fragments to colocate data requirements with child components, ensuring the loading state (rendered by the dynamic import fallback) and the loaded state share identical markup structure.

## Key Components

- **`BillingSections`** — The primary exported component that renders the billing page body in a fixed order: read-only notice → test clock panel → test mode banner → usage counters grid → notices → auto top-up section → plan sections → invoices history.
- **`billingSectionsSubscriptionFragment`** — GraphQL fragment on `SubscriptionDetail` that aggregates fragment requirements from child components (`DeviceUsageCard`, `FreeAiTokensCard`, `PaidAiTokensCard`, `PlanSections`, `InvoicesHistory`).
- **`billingSectionsBillingPlanFragment`** — GraphQL fragment on `BillingPlanDetails` that forwards data to `PlanSections`.
- **`BillingSectionsProps`** — Props interface controlling read-only mode, Relay fragment keys, AI card visibility, and optional slot content (`paidAiCard`, `notices`, `autoTopUpSection`) for composition flexibility.

## Usage Example

```typescript
import { BillingSections } from './billing-sections';

function BillingUsageScreen({ queryRef }: { queryRef: SomeQuery$key }) {
  const data = usePreloadedQuery(query, queryRef);

  return (
    <BillingSections
      readOnly={isDesktopBuild}
      subscription={data.subscription}
      billingPlan={data.billingPlan}
      showAiCards={data.subscription?.plan.includesAi ?? false}
      onClockChanged={() => refetch()}
      notices={<AiBalanceAlert />}
      autoTopUpSection={<AutoTopUpSettings />}
    />
  );
}

// Loading fallback renders with null refs to show child-level skeletons
<BillingSections
  readOnly={false}
  subscription={null}
  billingPlan={null}
  showAiCards={false}
  onClockChanged={() => {}}
/>
```

Pass `subscription`/`billingPlan` as `null` during loading so each child component (e.g., `DeviceUsageCard`) renders its own skeleton state, keeping loading and loaded layouts structurally identical.
