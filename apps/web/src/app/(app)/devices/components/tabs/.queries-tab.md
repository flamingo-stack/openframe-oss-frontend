# queries-tab.tsx

A device detail tab component that displays the scheduled osquery reports assigned to a specific host, with search filtering and sticky toolbar support.

## Key Components

- **`QueriesTab`** — Main exported component rendering a searchable table of a device's scheduled queries. Accepts a single `device` prop (`Device | null`).
- **`QUERIES_TAB_SKELETON_ROWS`** — Constant (5) controlling how many skeleton rows render while data loads.
- **`QueriesTabProps`** — Interface defining the component's props (`device: Device | null`).

## Behavior

- Fetches the host's assigned query reports via `useHostQueries(device?.fleetId)` (the only host-scoped endpoint).
- Since that endpoint omits run interval/frequency, it cross-references the team-scoped `useQueries` list (keyed by `device?.fleetTeamId`) to join each report's `interval` by query ID.
- Builds `QueryTableRow[]` rows via `useMemo`, filtering by a case-insensitive search term against `name` and `description`.
- Each row links to `routes.monitoring.query(reportId)` and includes a "Query Details" row action.
- Renders distinct empty states via `TabEmptyState`:
  - No device loaded yet.
  - Device has zero assigned queries.
  - Search yields no matches (handled inside `QueriesTable`'s `emptyState` prop).
- Hides the search input entirely when the table is truly empty (no rows, no query, not loading), matching the table's hidden header in that state.
- Uses `useStickyToolbar` to keep the search bar pinned during scroll, and passes `stickyHeaderOffset` to `QueriesTable` so its header aligns correctly beneath the toolbar.

## Usage Example

```typescript
import { QueriesTab } from './queries-tab';
import type { Device } from '../../types/device.types';

function DeviceDetailPage({ device }: { device: Device | null }) {
  return (
    <div className="device-tabs-content">
      <QueriesTab device={device} />
    </div>
  );
}
```

This component is typically rendered as one tab panel within a device detail view, alongside sibling tabs (e.g., policies, software), and relies on `device.fleetId` and `device.fleetTeamId` being populated once the parent device record has loaded.
