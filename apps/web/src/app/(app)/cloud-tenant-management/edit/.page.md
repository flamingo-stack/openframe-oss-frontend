Next.js client page component for editing an existing tenant integration, supporting both legacy (v1) and current (v2) tenant management implementations behind feature flags.

## Key Components

- **`EditTenantPage`** — Default export; the route-level page component for editing a tenant by ID.
- **`useTenantManagementGate`** — Feature flag hook controlling whether tenant management is enabled at all (`'off'` triggers a 404).
- **`useTenantManagementV2Gate`** — Feature flag hook determining whether to render the v2 (`EditTenantView`) or v1 (`EditTenantViewV1`) implementation.
- **`useRequiredIdParam`** — Hook that extracts and validates the required `id` route param, redirecting to the tenant list or "new tenant" route if missing.
- **`TenantPageShell`** — Shared layout wrapper providing page title and error boundary handling.
- **`LoadingWhen`** — Conditional loading-state wrapper from `@flamingo-stack/openframe-frontend-core`, used to block rendering until feature flags resolve.

## Usage Example

This file is a Next.js App Router page and is rendered automatically based on file-based routing (e.g., at a path like `/cloud/tenant-management/[id]/edit`). It is not typically imported directly elsewhere:

```typescript
// Routed automatically by Next.js; example of the pattern used internally:
import { useRequiredIdParam } from '@/app/hooks/use-required-id-param';
import { routes } from '@/lib/routes';

const id = useRequiredIdParam(
  routes.cloudTenantManagement.list,
  routes.cloudTenantManagement.new()
);
```

## Notes

- The component avoids prematurely rendering with a stale "off" gate state by waiting for both `gate` and `v2` flags to resolve (`'loading'`) before showing content.
- The `key={id}` prop on both `EditTenantView` and `EditTenantViewV1` ensures component state resets when navigating between different tenant IDs.
- Returns `null` while the ID param is being resolved, and calls `notFound()` if tenant management is disabled entirely.
