# native-push-initializer.tsx

Client component that bootstraps native push notification support for the mobile shell. It requests notification permission, registers the device's FCM token, and wires notification taps to the app's client-side router for deep-linking. Renders nothing and is a no-op outside the native mobile shell.

## Key Components

- **`NativePushInitializer`** — React component (mounted once in the authenticated app layout) that:
  - Skips initialization entirely when not running inside the mobile shell (`isMobileShell()`) or when the subscription is locked (`useSubscriptionOpen()`).
  - Calls `initNativePush` with a callback that resolves the tapped notification's route via `resolvePushNotificationAction` and `tappedNotificationId`, then delegates navigation/read-marking to `followNotificationTap`.
  - Marks the tapped notification as read via `markNotificationReadById` once a route is resolved.
  - Logs (but does not throw) initialization failures, since `initNativePush` latches internally and a failure is terminal for the session.

## Usage Example

```typescript
// Mounted once near the root of the authenticated app layout
import { NativePushInitializer } from '@/components/native-push-initializer';

export function AppLayout({ children }: { children: React.ReactNode }) {
  return (
    <>
      <NativePushInitializer />
      {children}
    </>
  );
}
```

**Notes:**
- Registration (`registerPushDevice`) is a mutation and bypasses the subscription gate intentionally — a locked workspace has no notifications to deliver, so registration is skipped rather than failed.
- Routing logic lives entirely on the frontend: the push payload only carries a `type` and entity ids (or, for announcements, an explicit link), never a route string, since the backend has no knowledge of client-side URL structure.
- Unknown notification `type`s still resolve to a safe fallback (the notifications page).
