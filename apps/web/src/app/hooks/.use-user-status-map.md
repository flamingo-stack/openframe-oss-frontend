Client-side user id → status map over `GET /api/users`, for surfaces whose payload carries no user status. Since the backend exposed `User.status` on GraphQL, the only remaining consumer is the tickets domain (`/chat/graphql` denormalizes the assignee to an id + name snapshot with no status).

## Key Components

### `useUserStatusMap()`

Returns `{ statusById, isUserDeleted, isUserSelfDeleted, isLoading }`:

- `statusById` — `Map<rawUserId, UserStatus>` built from the full users list (`usersQueryKeys.list(0, 1000)` — same cache key the employees page uses).
- `isUserDeleted(id)` — accepts raw ids AND Relay global ids (`User:<id>` base64, decoded via `decodeGlobalId`); answers whether the user is `DELETED` / `SELF_DELETED`.
- `isUserSelfDeleted(id)` — same id handling, `SELF_DELETED` only; used to hide the synthetic `deleted-{id}@deleted.invalid` email while admin-`DELETED` users keep showing theirs.

## Notes

- **Fail-open by design**: an id missing from the map answers "not deleted" — covers purged (`REMOVED`) users who never appear in `/api/users`, and viewers whose role can't list users (query error just leaves the map empty; deliberately no toast — the feature is decorative and a permissions-denied viewer would get a spurious error on every page).
- **Single page of 1000**: tenants beyond 1000 users would leave later users unmarked (fail-open). Accepted for now — the employees page itself has the same cap (`TODO: add pagination`), and the real fix is the `User.status` BE spec below.
- The `User.status` BE spec is DONE — scripts / worktime / KB read status from their own payloads and no longer use this hook. It stays for tickets until the chat service exposes assignee status (optional part of the spec).
- Consumers: tickets only — table columns / tabs, board (`tickets-board`, `board-assignee-picker`), ticket dialog `Assigned` blocks.
