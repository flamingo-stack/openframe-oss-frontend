# device-fields.ts

Defines the GraphQL fragment for the fullest device data shape consumed by the Devices page, representing the final rung in a three-step fragment ladder (`deviceSelectorFields_machine` → `deviceRowFields_machine` → `deviceFields_machine`).

## Key Components

- **`deviceFieldsFragment`** — An `@inline` GraphQL fragment on `Machine` that spreads `deviceSelectorFields_machine` and adds the remaining fields needed for full device detail views: `ip`, `macAddress`, `osUuid`, `agentVersion`, `osVersion`, `osBuild`, `timezone`, `registeredAt`, `updatedAt`, and the `toolConnections` list (including `id`, `machineId`, `toolType`, `agentToolId`, `status`, `metadata`, `connectedAt`, `disconnectedAt`).

This fragment is paired with a `machineToDevice` transform function (defined elsewhere) that reads it via `readInlineData`, since `@inline` fragments are consumed outside of React components as plain data, not through `useFragment`.

## Usage Example

```typescript
import { readInlineData } from 'react-relay';
import { deviceFieldsFragment } from './device-fields';

function machineToDevice(machineRef: any): Device {
  const machine = readInlineData(deviceFieldsFragment, machineRef);

  return {
    id: machine.id,
    ip: machine.ip,
    macAddress: machine.macAddress,
    osVersion: machine.osVersion,
    toolConnections: machine.toolConnections,
    // ...plus all fields inherited from deviceSelectorFields_machine
  };
}
```

Because `Machine implements Node`, Relay normalizes records by `id`, so data read through this fragment stays consistent with the same machine displayed in list rows, selector pickers, or detail tabs elsewhere in the app. Only spread this fragment where the full device detail payload is actually needed — lighter views should use `deviceRowFields_machine` or `deviceSelectorFields_machine` instead to avoid unnecessary fan-out cost.
