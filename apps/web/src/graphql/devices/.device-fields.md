Step 3 — the full device row, an `@inline` fragment on `Machine` that spreads `deviceSelectorFields_machine` and, through it, `deviceRowFields_machine`.

## Why a ladder of fragments

The infinite list, the bounded pickers and the schedule tables all feed the same `Device` shape into the same shared tables, but they afford different amounts of fan-out — `assignedDevices` resolves per machine and has timed out once on test-dev. So the field set is split into three steps, each spreading the one below it:

| Fragment | Adds | Spread by |
|---|---|---|
| `deviceRowFields_machine` | identity, status, last-seen, customer, tags | `script-schedule-devices-relay.ts` |
| `deviceSelectorFields_machine` | hardware ids, customer contact email | `schedule-device-picker-relay.ts` (both halves) |
| `deviceFields_machine` | network, OS detail, tool connections | `devices-list-relay.ts`, `devices-page-relay.ts` |

Each step has its own transform (`machineRowToDevice` / `machineSelectorToDevice` / `machineToDevice`), so a list gets a mapper typed to exactly what it selected. Spreading makes that structural instead of a convention several documents are each trusted to follow.

`@inline` does accept `@argumentDefinitions` + `@include(if:)`, but a conditional field lands in `$data` as `field?:` — i.e. back to "everything optional", which is what the ladder exists to avoid.

Select a field WHOLE at one step: `tags` sits entirely on the row step, because a field split across two steps lands in two different `$data` types with nothing to join the halves on. Different sub-fields of a linked record are fine — the row step reads `organization { name image }`, step 2 reads `organization { contactInformation }`.

`Machine implements Node`, so Relay normalizes these records by `id` across every query that spreads this — the list, a picker and a schedule tab read one record. That is what keeps device state consistent between screens; react-query could only ever hold a separate copy per cache key.

## Why `@inline`

The consumers are the `machine*ToDevice` functions in `devices/utils/device-transform.ts`, plain functions that flatten a row into the flat `Device` the shared tables render — not components. `readInlineData` is how a fragment's data is read outside React; without it the spread hands back an opaque fragment reference and every row needs its own `useFragment` component.

Nested spreads read the same way: `machineToDevice` reads this fragment, then hands the result — which carries the child fragment's spread — to `machineSelectorToDevice`, and so on down.

`readMachineEdges` (`devices/utils/read-machine.ts`) maps a connection's edges through step 3.
