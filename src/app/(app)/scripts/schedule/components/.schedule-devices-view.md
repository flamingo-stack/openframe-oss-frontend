Relay-powered "Edit Devices" page for a script schedule: two ways to target devices — an explicit machine set, or a stored rule the server resolves live.

## Key Components

| Export / Component | Description |
|---|---|
| `ScheduleDevicesView` | Root export. Reads the schedule's device SETTINGS, renders the info bar + mode radio, and mounts whichever half the mode names. |
| `SchedulePickerLists` | The **specific** half: available / assigned lists. Every +/− commits immediately through the incremental add/remove mutations — which is why the page exits via "Done" rather than a Save. |
| `ScheduleCriteriaPicker` | The **criteria** half: customer / type / OS fields over a live preview. One value, committed behind an explicit "Save Devices". |
| `SchedulePickerSkeleton` | The real `DeviceSelector` in its loading state, for the half being switched TO — the mode is known there, it is what the user just clicked. Locked with `disabled`, never `readOnly`: `readOnly` forces `singleSelect`, which drops the Available / Selected tab strip the loaded card has. |

## Usage Example

```typescript
// Render the Edit Devices page for a given schedule
<ScheduleDevicesView scheduleId="U2NoZWR1bGU6MTIz" />
```

## Key Behaviors

- **Three-query split**: `scriptScheduleDevicesSettingsRelayQuery` answers "which mode?" (plus the info bar's fields) — deliberately NOT the full detail query, which would make that answer wait behind the `scriptBody` of every script the schedule runs. Each half then issues its own device query, so the heavy list loads under a page that is already drawn, and the assignment's per-machine resolution is paid only by the half that renders it.
- **Mode is derived, not seeded**: `selectionMode = modeOverride ?? storedMode`. Until the user touches the radio the stored answer is what renders — no seeding effect, and no flash of the specific picker on a criteria schedule.
- **Radio and info bar sit ABOVE the boundary**: each half is its own data island, so switching unmounts one subtree and mounts the other; a radio drawn inside would remount and blink the control that was just clicked.
- **Two loading states, and the tab strip belongs to the second**: while the settings query is out the route skeleton draws the title, Back, the info bar and the mode block itself — real, locked, nothing marked (`value=""`) — but no picker, since its two halves are different surfaces. Once the settings land, the radio unlocks onto the stored mode and `SchedulePickerSkeleton` for THAT mode (tab strip and all) sits under its own boundary while the devices load. Waiting for the small query is what turns that second skeleton from a guess into a fact.
