Zustand store for ticket detail chat: per-side (client/admin) identity, cache concerns, and a converted **read mirror** of the core library's stream reducer. Message accumulation lives in the lib reducer — two instances per dialog, keyed `(dialogId, 'client')` and `(dialogId, 'admin')` — reached through `createReducerMirror` in `@/lib/chat-stream-thread`.

## Key Components

### Types

- **`ChatSide`** — `'client' | 'admin'` discriminator for the dual-pane view, and the mirror key
- **`SideState`** — per-side slice: `messages`, `phase`, `streamingId`, token usage, stream-sequence bookkeeping
- **`ApprovalStatusMap`** — approval state keyed by request id, shared across both sides (request ids are global)
- **`TicketDetailsStore`** — full store interface

### Why two reducers and not one

The two sides run **independent** JetStream subscriptions with separate seq spaces, so a dialog-keyed gate would drop one side's catch-up replay. Exactly two operations fan out across sides — approval resolution by `requestId` and tool merge by `execId` — and both come from the dialog store's built-in idempotent projection, not from app-side fan-out.

### Store Actions

| Category | Key Actions |
|---|---|
| **Messages** | `setMessages` (hydration), `addMessage`, `updateMessage`, `removeMessage`, `prependMessages`, `prependWithBoundaryMerge` |
| **Sending** | `pushOptimisticSend` |
| **Approvals** | `updateApprovalStatusInMessages`, `setApprovalStatus`, `upsertApprovalStatuses` |
| **Phase** | `setTyping`, `getTyping`, `getStreamingId` |
| **Lifecycle** | `clearChatState`, `clearSide` |

`setMessages` goes through `mirror.hydrate`: restoring a turn needs `resumed`, the accumulator seed and the adopt-once flag together (see `HydrateOptions`), and splitting those steps is what let a mid-stream reload wipe the persisted head of a turn.

## Usage Example

```typescript
import { useTicketDetailsStore } from './ticket-details-store';

// Reading messages for the admin pane
const adminMessages = useTicketDetailsStore(s => s.admin.messages);

// Hydrating a side from history (merge result)
useTicketDetailsStore.getState().setMessages('client', mergedMessages);

// Realtime chunks — through the shared per-side processor
const processChunk = useSideChunkProcessor('client', { onApprove, onReject });

// Switching tickets — reset all state
useTicketDetailsStore.getState().clearChatState();
```

## Notes

- Wire-protocol enums (`MESSAGE_TYPE`, `CHAT_TYPE`, `OWNER_TYPE`, `APPROVAL_STATUS`) are re-exported from the core library; only app-local ones (`DIALOG_STATUS`, `TICKET_STATUS`, `NATS_TOPICS`, `ASSISTANT_CONFIG`) stay in `tickets/constants`.
- `highestStreamSeq` feeds the history/realtime merge, which dedupes replayed synthetics already persisted to history.
- `prependWithBoundaryMerge` patches the row straddling a page boundary when paginating older history in.
