A null-rendering side-effect component that marks a ticket "read" once that ticket's client chat is the pane on screen - on two independent ledgers: the caller's notifications about the ticket, and the dialog's unread client messages.

## Key Components

### `TicketNotificationsAutoReader({ ticketId, dialogId, clientChatOnScreen, lastClientMessageId })`

Renders `null`.

1. **Notifications (per user)** - commits `markNotificationsReadForEntity(TICKET, ticketId)` through `useMarkEntityNotificationsRead`, which feeds the bell, the drawer and the sidebar count.
2. **Messages (shared by all technicians)** - commits `markDialogMessagesRead(dialogId)` through `useMarkDialogMessagesRead`, which resets `Ticket.unreadMessageCount` (the board card's "New Message" tag and the table's count) and zeroes it in the cached board/table pages.

| Prop | Type | Description |
|---|---|---|
| `ticketId` | `string` | Raw ai-agent ticket id — the same id `Ticket.unreadNotificationCount` is keyed on. Not a Relay global id. |
| `dialogId` | `string \| null` | The ticket's client-chat dialog id. Registered as an active dialog view while the chat is on screen (live message notifications for it are suppressed and auto-read), and the id the message counter is reset on. |
| `clientChatOnScreen` | `boolean` | Whether the client chat pane is actually being shown. Derived by `TicketDetailsView`, the only place that knows which layout column the viewport is showing. |
| `lastClientMessageId` | `string \| null` | Id of the newest END-USER row the chat shows (`lastClientMessageId()` in `utils/client-chat-read.ts`). Every new value re-arms the message mark; technician and assistant rows do not move it. |

## Key Behaviors

- **Fires only when the chat is on screen.** The notifications mutation is entity-scoped with no type filter, so it clears the ticket's chat-message notifications too. Those route to `?tab=chat` precisely so `notificationTargetsLocation` will not auto-read them from the Details tab — firing on mount would mark a customer's message read sight-unseen. Full contract on `useMarkEntityNotificationsRead`. The message mark carries the same gate: on the Details tab the user is not watching the conversation.
- **Session gated** on `isSessionActive({ idleAfterMs: ATTENTION_IDLE_MS })`, both ledgers re-running on the `subscribeAttention` edge (focus edges plus the first input after the attention window), so a tab the browser restored into the chat with nobody watching neither retracts the user's phone banner nor drops the board badge for the other technicians.
- **Notifications: feature-flag gated** on `notifications`, like every other consumer of notification data (`EntityViewAutoReader`, `UnreadCountsHydrator`), and **once per ticket per mount** (`markedReadTicketRef`), so returning to the chat does not re-invalidate the lists. Later arrivals fall to `EntityViewAutoReader`.
- **Messages: NOT flag gated** (the counter is unflagged on the ai-agent and the board renders it regardless) and **once per (dialog, newest client message)** (`markedMessageRef`): a message loaded with the history or arrived live while the chat is attended is marked at once, so no badge is left behind for something the technician watched arrive. An arrival nobody was there for stays armed until the next attention edge. Since the counter is shared, one technician reading the chat clears the badge for all of them (product decision, 2026-09-23).
- **Writes the badge rather than invalidating** (`clearCachedUnreadMessages`, before and after the request - see `useMarkDialogMessagesRead`). Invalidation only marks the board/table stale while they are unmounted behind this page, so navigating back painted the cached pages and the card kept its badge until the column's 15s poll.
- **Owns its own state** rather than living in the page component: the activity subscription ticks on every focus/blur, and holding it there would re-render the chat list and every info section each time the user alt-tabs.

## Usage Example

```tsx
// Inside TicketDetailsView
const clientChatOnScreen = hasClientChat && (mainTab === 'chat' || (useLgUp() === true && !showDetailsTabs));
const newestClientMessageId = lastClientMessageId(clientMessages);

<TicketNotificationsAutoReader
  ticketId={ticketId}
  dialogId={messageDialogId}
  clientChatOnScreen={clientChatOnScreen}
  lastClientMessageId={newestClientMessageId}
/>
```

## Notes

- `clientChatOnScreen` cannot be read off `?tab=` alone. A ticket with no description and no assigned items has nothing to put in a Details tab, so the desktop column renders the chat bare with `mainTab` still `'details'` — that is every ticket the AI dialog opens. The mobile column keeps its tabs there (the desktop sidebar's info/attachments/tags fold into them), so the two always-mounted columns disagree and only the breakpoint separates them. `useLgUp()` uses the same 1280px the core Tailwind preset gives `lg:`, and its `undefined` (viewport not yet known) reads as "not on screen", deferring the mark-read by a tick.
- Other technicians learn about the reset from the board column's poll (15s) or their next list fetch: the ai-agent publishes no live event for the counter.
