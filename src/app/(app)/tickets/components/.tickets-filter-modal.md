Mobile-only modal component that provides a buffered filter interface for ticket filtering by customer (organization) and assignee, preventing race conditions from sequential URL state writes.

## Key Components

### `TicketsFilterModal`
The primary exported component. Wraps `SimpleModal` with two filter controls and local state buffering — selections are held internally until the user explicitly applies or resets them.

**Props (`TicketsFilterModalProps`):**

| Prop | Type | Description |
|------|------|-------------|
| `isOpen` | `boolean` | Controls modal visibility |
| `onClose` | `() => void` | Callback to close the modal |
| `organizationIds` | `string[]` | Currently active organization filter values |
| `assigneeIds` | `string[]` | Currently active assignee filter values |
| `onApply` | `(filters) => void` | Flushes both filters atomically in a single call |

**Internal behavior:**
- Local state (`localOrganizationIds`, `localAssigneeIds`) is re-synced from props each time the modal opens via `useEffect`
- **Reset** calls `onApply` with empty arrays and closes
- **Apply** calls `onApply` with current local selections and closes

## Usage Example

```typescript
<TicketsFilterModal
  isOpen={isFilterOpen}
  onClose={() => setFilterOpen(false)}
  organizationIds={activeOrgIds}
  assigneeIds={activeAssigneeIds}
  onApply={({ organizationIds, assigneeIds }) => {
    setSearchParams({ organizationIds, assigneeIds });
  }}
/>
```

## Notes

- Designed for **mobile viewports** — desktop filter controls are rendered inline elsewhere
- The `onApply` single-callback pattern avoids URL clobbering that would occur with two sequential writes (e.g., updating `organizationIds` then `assigneeIds` separately in a URL-based state manager)
