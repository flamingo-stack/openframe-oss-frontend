Encapsulates the tag deletion flow for ticket contexts — managing confirm-dialog state, executing the delete mutation, and triggering a tag-list refetch.

## Key Components

| Export | Type | Description |
|---|---|---|
| `useTicketTagDelete` | Hook | Orchestrates the full tag-delete lifecycle for ticket views |
| `requestDelete` | `(id: string) => void` | Triggers the confirm dialog for a given tag ID |
| `isDeleting` | `boolean` | Mutation in-flight state for pending UI feedback |
| `dialog` | `JSX.Element` | Pre-wired `TagDeleteConfirmDialog` ready to render in the caller |

## Usage Example

```typescript
function TicketTagsSection({ ticketId }: { ticketId: string }) {
  const [selectedTags, setSelectedTags] = useState<string[]>(['tag-1', 'tag-2']);

  const { requestDelete, isDeleting, dialog } = useTicketTagDelete((deletedId) => {
    // Drop the tag from local selection on success
    setSelectedTags(prev => prev.filter(id => id !== deletedId));
  });

  return (
    <>
      {selectedTags.map(id => (
        <TagChip
          key={id}
          id={id}
          onDelete={() => requestDelete(id)}
          disabled={isDeleting}
        />
      ))}
      {/* Render the managed confirm dialog */}
      {dialog}
    </>
  );
}
```

## Notes

- `onTagDeleted` is called **after** a successful delete, allowing both live ticket state and form state callers to stay in sync without duplicating mutation logic.
- The dialog resolves the tag's display name internally via `useTicketLabels`, so callers only need to pass the tag ID to `requestDelete`.
- Safe to use in both the ticket detail view and the create/edit tag field — the callback pattern is the only integration point.
