Implements the `TicketService` class, which bridges the OpenFrame ticket GraphQL API to the internal `Dialog`-based abstraction used across the frontend, handling data fetching, normalization, status transitions, board reordering, messaging, and approvals.

## Key Components

### `TicketService` (class)
Implements `TicketServiceInterface` with the following methods:

| Method | Description |
|---|---|
| `fetchDialogs(params)` | Fetches a paginated, filtered list of tickets mapped to `Dialog` objects (filters: `statusIds`, `organizationIds`, `assigneeIds`, `tagIds`, `unreadOnly` → `filter.hasUnreadNotifications: true`, only ever sent as `true`; plus `search`) |
| `fetchBoardColumnByStatusId(params)` | Fetches tickets for a specific Kanban board column by status ID (same filters passed as flat variables, plus `activity` — an array of activity states for the board's activity/staleness filter, sent only when non-empty) |
| `fetchDialog(id)` | Fetches a single ticket by ID and returns it as a `Dialog` or `null` |
| `fetchMessages(params)` | Fetches paginated chat messages for a dialog via `/chat/graphql`; normalizes `messageData` aliases through `normalizeMessageDataAliases` (single parse point) |
| `transitionTicket(ticketId, toStatusId)` | Transitions a ticket to a custom status definition ID; throws on `userErrors` or missing ticket |
| `fetchTicketStatusTransitionRules()` | Fetches allowed status transitions as `{ from, to[] }` of status definition IDs |
| `reorderTicket(params)` | Reorders a ticket on the board (`afterTicketId`/`beforeTicketId`, optional `statusId` for cross-column moves); returns the resulting `DialogStatus` |
| `sendMessage(dialogId, content, chatType)` | Sends a chat message via REST |
| `approveRequest(requestId)` / `rejectRequest(requestId)` | POSTs approve/reject for a pending approval request |
| `fetchChunks(dialogId, chatType, fromSequenceId?)` | Fetches streaming chunk data; returns `[]` on failure (logs, does not throw) |

### `normalizeTicketToDialog(ticket)` (internal)
Maps a raw `TicketNode` GraphQL response shape to the frontend `Dialog` type, including status definition fields (`statusId`/`statusName`/`statusColor`/`statusKind`), `availableTransitions`, notes, tags, attachments, token usage, pending approval, `resolvedBy`, `escalatedByUser`, and the board activity indicator fields `lastActivityAt` (null when absent) and `activityState` (`TicketActivityState` — drives the staleness/activity chip on board cards).

### Status Mapping
- `TICKET_TO_DIALOG_STATUS` — one-way ticket→dialog status string map (ACTIVE, TECH_REQUIRED, ON_HOLD, RESOLVED, ARCHIVED); unknown statuses pass through as-is.

## Usage Example

```typescript
import { TicketService } from './ticket-service';

const service = new TicketService();

// Fetch paginated tickets
const page = await service.fetchDialogs({
  statusIds: ['status-def-id'],
  limit: 20,
});

// Fetch one board column, stale tickets only
const column = await service.fetchBoardColumnByStatusId({
  statusId: 'status-def-id',
  limit: 20,
  activity: ['STALE'],
});

// Transition to a workflow status
await service.transitionTicket('ticket-id-123', 'status-def-id-456');
```
