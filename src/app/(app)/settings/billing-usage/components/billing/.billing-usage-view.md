Renders the Billing & Usage settings page, orchestrating subscription status display, usage metrics, cancellation flow, and invoice history via a multi-step modal workflow.

## Key Components

| Export / Symbol | Description |
|---|---|
| `BillingUsageView` | Public entry point; wraps `BillingUsageContent` in a `<Suspense>` boundary with a skeleton fallback |
| `BillingUsageContent` | Internal component that fetches billing data via Relay (`billingUsageViewQuery`), computes UI state, and renders the full page |
| `billingUsageViewQuery` | GraphQL query (Relay) fetching `subscription` data including pending invoices |
| `cancelStep` state | Four-step FSM — `'idle'` → `'reason'` → `'offer'` → `'cancelled'` — driving the cancellation modal sequence |
| `primaryAction` | Dynamically resolves the page's primary CTA based on subscription flags: Renew / Pay Overage / Activate / Update |
| `menuActions` | Injects a "Cancel Subscription" menu item only when the subscription is `ACTIVE` and the `cancelSubscription` feature flag is enabled |
| `refreshKey` | Integer bumped after a `resumeSubscription` mutation to force a Relay network refetch (workaround for Boolean-only mutation response) |

## Usage Example

```typescript
// Mount in a settings route — Suspense and data fetching are self-contained
import { BillingUsageView } from './billing-usage-view';

export default function BillingPage() {
  return <BillingUsageView />;
}
```

```typescript
// The cancellation flow progresses through steps automatically:
// 1. User clicks "Cancel Subscription" → step = 'reason'
// 2. User selects a reason → step = 'offer'  (CancelOfferModal shown)
// 3. Mutation completes  → step = 'cancelled' (SubscriptionCancelledModal shown)
// 4. Modal dismissed     → step = 'idle'
```

## Notes

- `TestClockPanel` and `TestModeBanner` are dev/test-only; they no-op in production unless the test-clock env flag is set.
- Device and AI usage cards adapt their layout: single column when AI is disabled, two columns when `flags.hasAi` is true.
- The "Next Payment" row is intentionally hidden during active trials to avoid rendering a misleading `$0` value.
