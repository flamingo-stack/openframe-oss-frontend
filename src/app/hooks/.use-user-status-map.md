Client-side user id → status map over `GET /api/users`, for surfaces whose payload carries no user status (GraphQL `User` is a status-less stub; tickets denormalize the assignee).

## Key Components

### `useUserStatusMap()`

Returns `{ statusById, isUserDeleted, isLoading }`:

- `statusById` — `Map<rawUserId, UserStatus>` built from the full users list (`usersQueryKeys.list(0, 1000)` — same cache key the employees page uses).
- `isUserDeleted(id)` — accepts raw ids AND Relay global ids (`User:<id>` base64, decoded via `decodeGlobalId`); answers whether the user is `DELETED` / `SELF_DELETED`.

## Notes

- **Fail-open by design**: an id missing from the map answers "not deleted" — covers purged (`REMOVED`) users who never appear in `/api/users`, and viewers whose role can't list users (query error just leaves the map empty; no toast).
- Interim solution: a BE spec exists to expose `status` on the GraphQL `User` type, after which GraphQL surfaces can drop this join.
- Consumers: tickets table columns / tabs, scripts-v2 executions & runs & authors, worktime table, KB article author.
